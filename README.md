# Sprite Generator

Three Claude Code skills that take a screenshot, several separate reference
images, one clean picture, or nothing but words, and turn it into game
sprites. There is no image-generation API anywhere in this pipeline: a sprite
is either drawn by Python code, or generated by hand in Gemini or ChatGPT and
cut out locally.

## Install as a Claude Code plugin

The three skills ship as one plugin; `.claude-plugin/` holds both manifests, so
this repo is its own single-plugin marketplace.

```bash
claude plugin marketplace add masa2146/sprite-generator   # or a local clone's path
claude plugin install sprite-generator@sprite-generator
```

`plugin.json` points `skills` at `./.claude/skills` rather than moving the
directory: `tests/conftest.py` puts `.claude/skills/sprite-brief/scripts` on
`sys.path`, so a test imports the exact modules the skill runs. Installed and
in-repo are the same files, not two copies that can drift.

Uninstall with `claude plugin uninstall sprite-generator` and
`claude plugin marketplace remove sprite-generator`.

## Skills

| skill | job |
|---|---|
| [`sprite-brief`](.claude/skills/sprite-brief/SKILL.md) | turns the input into `analysis.json`, cropped `refs/`, and a `review.html` |
| [`image-style`](.claude/skills/image-style/SKILL.md) | resolves the whole set's look into six fields — `render`, `camera`, `lighting`, `palette`, `linework`, `realism` |
| [`procedural-sprites`](.claude/skills/procedural-sprites/SKILL.md) | writes the Python that draws each sprite |

`procedural-sprites` draws geometry, not texture: hair, cloth folds and
painted faces are not in its lane and will not be — those still come from
the hand-generation path below.

Ask Claude Code to use `sprite-brief` with whatever you have — a screenshot, a
folder of pictures, or just a description of what you want. It calls
`image-style` for you, and hands off to `procedural-sprites` (or to the
hand-generation path) once you've reviewed the brief. You don't normally
invoke `image-style` or `procedural-sprites` directly.

## The chain

```
screenshot / images / words
        │
        ▼
   image-style        resolves render / camera / lighting / palette / linework / realism,
        │             field by field: the user's words > the style image > reference image(s) > default
        ▼
   sprite-brief        decides each object's crop shape, cleans the crop, measures its
        │              real palette, writes analysis.json + refs/ + review.html
        │
        ├── procedural-sprites   one shared style.py + one script per asset → out/<asset>.png
        │
        └── hand generation       paste review.html's prompt blocks into Gemini/ChatGPT,
                                   cut the downloads with cut.py
```

Both drawing paths run from the same `analysis.json`. That split is the
point: the brief is the one place the input gets decided, and everything
after it is a choice of *how* to render, not *what* to render.

## `analysis.json`

One file per set. Image paths inside it (`style_image`, each object's
`source`) resolve against the file itself, not the working directory, so the
file travels with its own pictures.

```json
{
  "style": {
    "render": "soft 3D render, glossy plastic material",
    "camera": "3/4 front view, slight high angle",
    "lighting": "top-left key light, soft ambient occlusion",
    "palette": "#FF6B4A #4ECDC4 #FFE66D",
    "linework": "no outline, rounded geometry",
    "realism": "stylized cartoon"
  },
  "style_source": {
    "render": "kullanıcı", "camera": "stil görseli", "lighting": "stil görseli",
    "palette": "ölçüm", "linework": "varsayılan", "realism": "kullanıcı"
  },
  "style_image": "screenshot.png",
  "objects": [
    {
      "id": "conveyor_belt_frame",
      "source": "screenshot.png",
      "bbox": [30, 140, 690, 1010],
      "views": ["top_down", "three_quarter"],
      "subject": "what this object IS, briefly",
      "form": "its construction: how many parts, arrangement, proportions",
      "detail": "distinguishing smaller features",
      "state": "optional — e.g. 'empty, without the object it normally holds'",
      "flatten_rows": false,
      "blank": [[30, 40, 90, 70]]
    }
  ]
}
```

| field | meaning |
|---|---|
| `style.*` | the six style fields, HOW the whole set looks — must never name an object |
| `style_source.*` | where each style field came from: `kullanıcı`, `stil görseli`, `referans`, `ölçüm`, or `varsayılan` when nobody claimed it |
| `style_image` | the shared screenshot, if there is one — the picture boxes get cut from |
| `objects[].id` | matches `^[A-Za-z0-9][A-Za-z0-9_-]*$`; becomes a filename |
| `objects[].source` / `bbox` | which of the three crop shapes this object gets — see below |
| `objects[].views` | closed pool: `front`, `three_quarter`, `side`, `back`, `top_down`, `rotated_45`, `rotated_90`, `rotated_135` |
| `objects[].subject` / `form` / `detail` / `state` | what the object is, its construction, its distinguishing features, and an optional named state |
| `objects[].flatten_rows` | for a straight run — a rail, a belt — flattens colour along the run instead of correcting a lighting ramp across it |
| `objects[].blank` | source-image boxes painted out of this object's own crop before anything sees it |

Numbers, letters and labels are gameplay variables, not design: never put a
glyph or its value in `subject`, `form` or `detail` — describe the blank
surface that carries it instead.

Cropping is a decision, not a default, and it has exactly three shapes:

| the object has | its reference is |
|---|---|
| a `bbox` | cut from its own `source`, or the shared `style_image` when it names none |
| a `source` but no `bbox` | that whole picture, cleaned but uncut |
| neither | carried by its description alone — no picture at all |

## Workspace and its venv

Everything a job produces lives under `sprites-generated/<set>/`, gitignored:

```
brief/    analysis.json · review.html · refs/
scripts/  style.py · <asset>.py · sprite_lib.py + sdf3d.py + character_lib.py (copied in, not imported)
out/      the sprites themselves
qc/       _qc_sheet.png · cmp_<id>.png
```

Drawing sprites in code runs through its own interpreter, never the system
one, whose packages are not this project's business:

```bash
[ -x sprites-generated/.venv/bin/python ] || {
  python3 -m venv sprites-generated/.venv
  sprites-generated/.venv/bin/pip install -q pillow numpy
}
sprites-generated/.venv/bin/python sprites-generated/<set>/scripts/<asset>.py
```

`sprite-brief`'s own scripts (`brief.py`, `cut.py`) ship with the skill, not
with a generated set, and are run with a plain `python3` that has `pillow`
and `numpy` importable — the only two dependencies anywhere in this repo:

```bash
python3 .claude/skills/sprite-brief/scripts/brief.py \
    --analysis analysis.json --out-dir sprites-generated/<set>/brief --no-open
```

If plain `python3` lacks `pillow`/`numpy` — this step can run before the venv
above ever exists — fall back to `sprites-generated/.venv/bin/python` the same
way, per `sprite-brief/SKILL.md`.

## The hand-generation path

If you'd rather not draw in code, `review.html`'s second half is a
paste-ready prompt per object per view, generated from `prompts.py` — the
same module the review page itself reads, so the two paths never carry
different wording. For each prompt: paste it, and upload **both** the
object's own crop and `refs/_style.png`. Every message must carry both — the
image model does not see the chat history, so a screenshot uploaded once at
the top never reaches the later generations, and the style drifts. Start a
fresh chat per set.

Cut what comes back:

```bash
python3 .claude/skills/sprite-brief/scripts/cut.py <downloads> --out-dir sprites-generated/<set>/out
```

| flag | when |
|---|---|
| *(default)*, same as `--key` | a sheet of objects on one flat backdrop colour — floods that colour in from the border, so a dark seam inside an object survives |
| `--glow` | a soft additive effect with no hard edge — alpha comes from brightness instead |
| `--tol` (default 14) | widens what `--key` counts as the background colour |

## Why the flat grey backdrop

Every prompt asks for `isolated on flat solid #808080 neutral grey
background` rather than transparency, because hosted image models do not
reliably emit an alpha channel. The choice of grey over an easy-to-key
colour like magenta is a measurement from when this pipeline cut backdrops
with an alpha-matting model: matting returns edge pixels as a blend of
subject and backdrop, so a saturated backdrop bleeds colour into that blend.
Measured on a synthetic sprite across four subject colours (teal, white,
grey, gold), a `#FF00FF` backdrop left 610–2079 tinted edge pixels every
time; `#808080` left zero. That matting model is gone — `cut.py --key`
floods the backdrop colour in from the border instead — and grey has not
been re-measured against it. It stayed the default because a border flood
still needs a backdrop colour no subject is likely to share, which is
reasoning carried forward from the original test, not a new measurement of
the current cutter.

## Tests

```bash
python3 -m pytest
```

No network, no model download, runs in a couple of seconds.

## Unity import

Set on each imported sprite: Texture Type `Sprite (2D and UI)`, `Alpha Is
Transparency` checked, Mesh Type `Tight`. Generating `.meta` files
automatically is not implemented.
